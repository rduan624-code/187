# 从 main 开始理解在线升级

先把这套程序理解为一条流水线：**网络收包 → 读协议字段 → 收齐文件 → 检查文件 → 选择目标 → 准备目标 → 烧写 → 回报结果**。不要一开始就看所有结构体或函数指针。

## 1. 文件分工

```text
main_sdk.c              启动网络，反复调用网络处理和升级处理
    ↓
upgrade_udp_sdk.c       接收 UDP、取出完整字节、发送 UDP 应答
    ↓
upgrade_app.c           决定下一步做什么，保存当前升级进度
    ├── icd_upgrade.c   解释协议字节、计算累加和、组装应答
    └── upgrade_board.c
          ├── A：本地 Flash 接口
          └── B/C/D：AXI/Aurora 远端接口

upgrade_config.h        把需要修改的配置集中起来
```

这与参考包的分工一致，但保留原版已经验证的协议策略。函数名称相似不代表参数完全相同；不要把两个版本的文件混合编译。

## 2. main_sdk.c：每一圈做什么

`main()` 前半段只执行一次：初始化平台、初始化 lwIP、填写 IP、添加网卡、启动 UDP 服务。

然后进入 `while (1)`。每一圈依次处理定时标志、调用 `xemacif_input()` 接收网络数据，再调用 `upgrade_udp_sdk_poll()` 推进升级。

为什么不在循环里直接调用收包回调？因为回调属于 lwIP：收到 UDP 数据时，lwIP 自动调用它。没有数据时，回调不会执行，主循环仍继续处理其他工作。

新的入口不启动旧 XVC TCP 服务。旧代码保留作参考，不影响这条升级调用链。

## 3. upgrade_udp_sdk.c：数据如何进来和出去

### upgrade_udp_sdk_init()

它先创建一个 `upgrade_config_t config`，逐项填写本机 UUID、模块号、四个目标的编号、镜像缓冲地址及大小，然后把发送和硬件函数的地址填进去。

例如：

```c
config.prepare = prepare_target;
```

这里没有括号，意思是“以后要准备目标，就调用 prepare_target 这个函数”。它不会在此刻启动硬件。这种写法叫函数指针；本版只在连接网络/硬件接口的地方使用，后面暂时把它当作普通函数调用即可。

接着调用 `upgrade_app_init()` 清空业务状态，调用 `udp_new()` 创建 UDP 控制块，`udp_bind()` 绑定 10001 端口，`udp_recv()` 注册 `on_udp_received()`。

### on_udp_received()

1. 从 `pbuf->tot_len` 得到完整 UDP 载荷长度。
2. 用 `pbuf_copy_partial()` 复制所有分段数据，不能只复制 `pbuf->len`。
3. 保存这份报文的发送端 IP/端口，调用 `upgrade_app_on_datagram()`。
4. 释放 lwIP 缓冲。

当前处理方式会立即解析这一帧并复制文件数据；不会把原始 `pbuf` 指针长期保存，也不会在回调中等待 Flash 烧写。

### send_report()

从业务层拿到完整应答，分配网络缓冲、复制字节、调用 `udp_sendto()`，最后释放网络缓冲。发送失败时返回非零，业务层保留应答，下圈再发。

### upgrade_udp_sdk_poll()

将当前毫秒计数传给 `upgrade_app_poll()`。这个计数来自 250 ms 平台定时中断，与报文里的年月日时间戳不是同一个东西。

## 4. icd_upgrade.c：不要把报文强转成结构体

网络收到的是一个 `uint8_t` 数组，每个元素就是一个字节。比如总长度 29，采用大端编码时两字节是 `00 1D`。

`icd_read_u16_be()` 把前面的字节放到高 8 位，再与后面字节合起来；`icd_write_u16_be()` 做相反的事情。32 位函数同理处理四个字节。

MicroBlaze BSP 是小端，ICD 是大端。显式逐字节读写可避免端序、结构体填充和非对齐访问问题。

### icd_parse_update()

按顺序检查：指针是否有效、实际长度是否合理、长度字段是否相等、是否为 F0/0008、保留字段及时间是否有效。全部通过后才按固定偏移读取目标、帧号和载荷。

`payload = data + 31` 表示载荷从第 31 号下标开始，不表示又分配了一份内存。调用方必须在原始数据还有效时使用它。

### icd_parse_summary()

第一帧载荷必须恰好 60 字节。函数检查 BCD 版本和日期，提取期望累加和、文件编号及文件长度，并保存原始摘要。

### icd_checksum_add()

每次接收一块数据，就把每个字节累加进去。它不是 CRC。摘要前四字节本来就是期望校验字，所以计算时跳过；剩下 56 字节摘要和文件内容都要计算。

### icd_build_report()

把源/目的 UUID 对调，填写本地递增的报告流水号、时间、F3 类型、ID 和实际长度，再写结果。

- 0088：`detail` 表示最近成功接收的帧号，写两字节。
- 0089：`detail` 表示故障码，写一字节。
- 008A：`detail` 表示进度编码，写一字节；4 才表示 100%，不是直接写 100。

## 5. upgrade_app.c：保存“现在做到哪一步”

`upgrade_app_t` 是当前会话的记事本，最先看懂这几个成员即可：

| 成员 | 含义 |
|---|---|
| state | 当前处于接收、准备、烧写还是已结束 |
| last_sequence | 最近成功保存的文件帧号 |
| received | 已保存多少文件字节 |
| metadata | 第一帧解析出的摘要 |
| sum | 当前累加和 |
| peer | 本次升级的发送端 IP/端口 |
| config.image | 真正保存镜像的数组地址 |
| pending / head / count | 待发送的应答队列、队首位置、报告数量 |

### upgrade_app_init()

检查缓冲和发送接口，清零进度，保存配置。不要在正在烧写时随意重新调用它，因为这会丢失当前进度；正常退出由状态机负责。

### upgrade_app_on_datagram()

代码里的中文“第一步～第五步”对应下面的操作：

1. 解析报文，确认发给本机、目标已启用、配置项/程序编号匹配。
2. 空闲状态下只接受序号 1；解析摘要，记录发送端和目标，初始化累加和。
3. 后续帧必须等于 `last_sequence + 1`。若第 3 帧先到，但本地只有第 1 帧，回 0088 失败和帧号 1。
4. 数据不能超过剩余文件空间；先 `memcpy()` 保存，再更新累计字节数与最近序号，然后应答成功。
5. 最后一帧到达时检查实际文件长度及累加和。通过后进入 `UP_PREPARING`，还没有开始烧写。

为什么还要检查发送者和目标？因为 UDP 不保证后面的数据一定来自同一个发送端。不能把第二个发送者或 B 卡的分帧追加到正在接收的 A 卡镜像。

### queue_report()

它把“已经组装好的应答”放到待发送队列，不直接等待网络。这样网卡短暂忙碌时，不会丢掉刚生成的应答。

队列是固定大小的数组：走到末尾再从开头使用。`% UP_REPORT_QUEUE` 只是让下标绕回开头。接收入口会预留最多三份应答的空间；空间不足时拒收新数据，避免“已经推进帧号却无法保存应答”。

### upgrade_app_poll()

每次主循环按顺序做三件事：先发送应答，再检查超时，最后推进一个硬件阶段。

| 状态 | 这一阶段做什么 |
|---|---|
| UP_IDLE | 等待新文件的首帧 |
| UP_RECEIVING | 接收文件分帧 |
| UP_PREPARING | 准备目标；A 检查存储，B/C/D 还要传数据并确认远端准备成功 |
| UP_WAIT_BURN | 0089 成功已经生成，等待应答队列发出后再启动烧写 |
| UP_BURNING | 查询硬件状态、发送进度；不会循环等待硬件完成 |
| UP_DONE | 保存成功结果，处理最后帧重传 |
| UP_FAILED | 保存失败结果，等待下一次任务或超时清理 |

`prepare` 只调用一次以启动目标准备，`prepare_step` 后续每圈查询。烧写同样由 `begin` 启动一次，再调用 `step` 查询。正因为这样分开，程序才能在 Flash 很忙时继续服务网络。

### report_load_failure() / report_burn_failure()

加载阶段失败用 0089，烧写阶段失败用 008A。两种失败都是真实失败，不能把“函数执行到了最后”当作硬件成功。

### reset_upgrade()

清空会话进度。它不随意清掉板级配置，也不是硬件复位命令。

## 6. upgrade_board.c：后面接驱动主要改哪里

先看 `upgrade_board_get_target_type()`：switch 明确把 0x71 分到本地，把 0x72/73/74 分到远端。其余目标返回无效。

然后按阶段阅读 `upgrade_board_prepare()`、`upgrade_board_prepare_step()`、`upgrade_board_begin()`、`upgrade_board_step()`。这些函数用普通 if 分别调用 `local_...` 或 `remote_...`，不用再跨三个文件找函数表。

| 函数 | 返回 0 | 返回 1 | 返回负数 |
|---|---|---|---|
| prepare | 已启动准备 | 不使用 | 无法启动 |
| prepare_step | 还在准备 | 目标已检查并准备好 | 准备失败 |
| begin | 已启动烧写 | 不使用 | 无法启动 |
| step | 还在烧写 | 镜像和摘要已验证持久化 | 烧写失败 |

注意：返回值约定保留本版已有行为，不要与参考包的 `0=操作完成、1=忙` 混用。

现在 `local_...` 和 `remote_...` 都有明确的待实现注释，返回失败。拿到手册后再补本地 Flash 驱动及远端通道。

`upgrade_board_abort()` 用于取消旧任务。当前没有真实任务可取消；接入硬件后，必须确保返回时旧 DMA/远端任务不会继续访问缓冲，才能开始下一次升级。

## 7. 第一次阅读可以先不深入的内容

先理解主调用链和每个状态做什么，再回头看环形队列、时间回绕和函数指针。它们用于解决网络忙、异常恢复和测试接入，不要求你先懂这些才能理解升级流程。

测试里的硬件模拟是为了检查业务流程，不能复制成实际 Flash 驱动。构建 SDK 时不要把 `tests/` 中含 main 的文件加入应用。
